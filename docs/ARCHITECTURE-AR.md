# بنية المنصة

واجهات العميل والمورد والإدارة منفصلة في المصدر، وتُنشر مبدئيًا تحت نطاق واحد لتبسيط الجلسات والتكلفة. لا تحتاج ثلاثة اشتراكات استضافة مستقلة في البداية. يستطيع تطبيق iPhone أو Android لاحقًا استخدام الخادم نفسه عبر HTTPS.

## توزيع المسؤوليات

| الجزء | المسؤولية |
|---|---|
| GitHub | حفظ المصدر والتغييرات، بعد ربط مستودعك |
| Vercel | تقديم HTML/CSS/JS وتشغيل نقطة دخول API |
| backend | المصادقة، التفويض، التحقق من الحقول، تنقيح البيانات وسجل الإجراءات |
| Supabase Auth | حسابات المستخدمين وتأكيد البريد وكلمات المرور والجلسات |
| PostgreSQL | الطلبات والعروض والاهتمامات والملفات التعريفية والإعدادات والصلاحيات |
| Supabase Storage | الصور في bucket خاص؛ الوصول عبر API بحسب صلاحية المستخدم |

## الجداول

- `profiles`: الدور والاسم والشركة والبريد والهاتف والدولة والصلاحيات وحالة الحساب.
- `requests`: صاحب الطلب وبياناته وصوره والترجمة وقائمة الموردين المدعوين والعرض المختار.
- `quotes`: المورد والطلب المرتبط وعرض السعر وحالة المراجعة والترجمة.
- `public_offers`: عروض الموردين المستقلة.
- `interests`: العميل والعرض العام الذي طلبه وحالة المتابعة.
- `media`: ملكية الصور ومكانها الخاص ونوعها.
- `settings`: النصوص العربية والإنجليزية والشعار.
- `audit_logs`: من نفذ الإجراء والتاريخ والسبب وحالة السجل قبل وبعد التغيير.
- `notifications`: أحداث الدعوة ونشر عرض السعر، مهيأة للعرض أو الإرسال لاحقًا.

العلاقات الأساسية معرفات وأعمدة PostgreSQL ومفاتيح خارجية. الحقول المتغيرة للمحتوى محفوظة في JSONB داخل كل جدول؛ ليست نسخة كاملة من حالة المتصفح في صف واحد. توجد فهارس للمالك والطلب والحالة وقائمة المدعوين. ترحيلات لاحقة تستطيع نقل الحقول المتكررة إلى أعمدة إضافية دون تغيير الواجهات كلها.

## الصلاحيات وإخفاء الهوية

تتحقق كل عملية في API من هوية Supabase ومن الدور والصلاحيات المحفوظة في `profiles`. لا يُعتمد على الدور المرسل من المتصفح. بيانات تسجيل الحساب الجديد لا تستطيع إنشاء مدير.

جداول العمل عليها RLS، وصلاحيات anon وauthenticated ملغاة عمدًا: هذه النسخة تتعامل مع الجداول عبر API فقط، باستخدام مفتاح خدمة موجود على الخادم. لأنه يتجاوز RLS، فإن تدقيق التفويض داخل API ضروري، ولا يكفي الاعتماد على إعدادات الجدول وحدها.

يستلم العميل عروضًا منقّحة دون هوية المورد أو النص الأصلي، ويستلم المورد طلبات المدعوين فقط دون هوية العميل أو عروض المنافسين. الإدارة ترى بيانات التواصل فقط مع صلاحية `accounts.read`. صلاحيات المراجعة تتيح الاطلاع على المحتوى الأصلي الضروري للمراجعة؛ قد يحتوي المحتوى المرفوع نفسه على هوية قبل تنقيحه، لذلك لا تمنح هذه الصلاحية لمن لا يجب أن يرى المحتوى الأصلي.

تُحفظ جلسات الويب في HttpOnly cookies. الكتابة من المتصفح تتطلب Origin مطابقًا. يدعم API أيضًا Bearer token موثقًا لتطبيق جوال؛ يمكن للتطبيق المستقبلي تسجيل الدخول عبر Supabase Auth ثم إرسال access token إلى API. لم يتم بناء تطبيق الجوال أو واجهة تسجيل دخوله في هذه الحزمة.

## سير العمل

العميل يرفع طلبًا، الإدارة تراجع النصوص والصور وتستبعد الصور التي تكشف الهوية وتكتب العربية والإنجليزية يدويًا، ثم تختار الموردين وتنشر الدعوة. المورد يرسل عرضًا واحدًا نشطًا لكل طلب. الإدارة تراجع عرضه وتنشره. العميل يختار عرضًا واحدًا؛ تمنع أرقام إصدارات السجلات الكتابات المتعارضة من تبويبين.

تستطيع الإدارة حفظ ترجمة مكتملة دون نشر. استبعاد الصور يحذفها من العرض المنشور ولا يمحو الملف الأصلي من التخزين. ليست هناك ترجمة آلية أو دردشة أو تواصل مباشر بين الطرفين.

الحذف قابل للاستعادة. حظر الحساب يمنع عملياته القادمة ويمنع عرض عروضه العامة للآخرين. سجلات الإدارة لا تُمحى عند الحذف. حماية المدير الرئيسي تمنع تعطيله عبر API.

## التوسع

البنية قابلة للتطوير دون رمي الواجهات والخادم. لكن عدد المستخدمين ليس المقياس الوحيد؛ حجم الصور والطلبات المتزامنة والاستعلامات يؤثر في التكلفة.

مبدئيًا يستخدم `/api/state` لقطة من البيانات المسموح بها فقط للحفاظ على الواجهات الحالية. تحميل اللقطة والبحث فيها مناسب لبداية صغيرة، لكنه **ليس تنفيذًا مكتملًا لـ100,000 مستخدم**. قبل زيادة حجم البيانات يلزم إضافة قوائم ذات صفحات وبحث على الخادم وعدادات مستقلة، وتحسين التحقق من صلاحية الصور بحيث لا يعيد تحميل اللقطة لكل صورة. الحد الحالي 20,000 سجل للقائمة يرفض الطلب برسالة واضحة بدل إخفاء النتائج الزائدة.

من التحسينات اللاحقة أيضًا: مهام إشعارات مؤجلة، حدود رفع لكل حساب، تنظيف الصور غير المرتبطة، نسخ احتياطية واستعادتها، مراقبة الأخطاء والأداء، واختبارات ضغط. يمكن إضافتها داخل البنية نفسها؛ زيادة الموارد وحدها لا تحل جميع مشاكل النمو.
